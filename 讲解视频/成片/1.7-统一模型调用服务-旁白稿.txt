1.7 统一模型调用服务
把原型演进为可配置、可部署、可验证的企业模型执行基础设施

说明：根据第一章学习笔记整理，采用本地中文合成旁白。

00:00  从原型走向独立服务
关键判断：保留已经验证的语义，再把边界工程化

上一节的单文件网关已经解决统一调用、结构校验、流式和恢复。本节保留这些语义，把配置、路由、提示词、审计和入口拆成独立服务边界。
企业差旅助手、客服助手和评测脚本一起接入后，模型配置不能散在业务代码里，调用记录也不能只留在进程内存中，服务需要可部署和可验证。
模型调用至少有传输、供应商、协议和语义四层成功。HTTP 返回成功，只证明得到响应，仍可能缺少结果字段、结构非法，或工具参数越权。
我们训练四类能力：构建闭环、判断工程取舍、给 AI 明确规格，以及决定平台怎样演进。目标是会证明可靠性，而不仅是运行成功请求。

00:59  完整调用链怎样分工
关键判断：策略、适配与任务状态由不同层负责

一次调用从兼容接口进入，先完成鉴权、限流和校验，再转为内部请求。随后固定提示词、结构、预算和关联上下文，才进入候选路由与执行。
能力注册表，也就是 Registry，描述有哪些端点以及能做什么。路由器根据本次请求产生候选顺序，适配器再负责发出具体供应商请求。
网关服务编排整次模型调用，校验器和事件映射器负责收敛结果。账本与追踪记录保存证据，不能由任意路由临时拼一份日志替代。
任务循环决定下一步，运行框架管理状态、预算、权限与取消。网关返回模型执行结果，不能因为文本里写了完成，就替任务修改终态。

原文依据：1.7 1.2 本节只沿哪一条主链推进？；1.7 二、先统一术语：Gateway、Router、Adapter 与 Harness 分别是什么？

01:57  分清已交付与扩展设计
关键判断：项目能力应以笔记声明和实际代码为准

笔记描述的项目提供聊天与响应兼容接口、模型列表和健康检查，并有多个供应商、公开模型别名、优先级路由与加权轮询。
还包括普通输出、流式、首块前恢复、本地结构复验和一次修复，提示词版本及沙箱渲染，用量写入 SQLite，并提供鉴权、基础限流和容器交付。
但笔记也明确保留边界：限流与熔断状态在单进程内存里，多副本需要共享存储；模型执行服务不维护完整 Agent 任务状态。
后面讨论的完整内部契约、取消治理、预算传播和更丰富观测，有些标为扩展设计。学习时不能把设计示例误认为项目已经全部实现。

原文依据：1.7 三、从 1.6 到 1.7：为什么要继续演进？；1.7 十五、项目实战：Mini LLM Gateway；1.7 六、第一阶段——统一协议

02:52  外部兼容终止在入口
关键判断：兼容接口降低接入成本，内部契约隔离变化

对外兼容使已有客户端容易接入，但字段长得一样，不代表各供应商行为相同。兼容协议应该在入口结束，内部使用平台自己的请求模型。
内部请求把消息、生成参数、输出格式、是否流式、提示词选择和关联上下文分开。这样参数变化与任务关联都有明确位置，不靠任意字典传递。
差旅助手请求结构化服务类别，而不是硬绑定某个供应商型号。部署配置和路由决定实际端点，上层关注业务所需能力。
规范化还要加入可信身份和追踪信息。租户不能由客户端请求正文自行声明，否则用户可能冒充其他租户，绕过配额或查看不属于自己的记录。

原文依据：1.7 6.1 OpenAI Compatible 是外部接口，不是内部领域模型；1.7 6.2 定义请求协议；1.7 7.3 请求规范化

03:49  结果和错误都是协议
关键判断：上层根据稳定语义决策，不猜供应商字符串

统一结果同时保留请求的逻辑模型和实际使用模型，再记录供应商、文本、结构对象、结束原因、用量、延迟与恢复次数。
结束原因很重要。正常结束、长度截断、内容过滤和取消不应该全变成成功文本，否则差旅助手可能把被截断的决策当作完整答案。
错误也必须是稳定协议。认证、限流、超时、上下文过长、输出非法和流中断，都应该有可用于决策的错误码，而不是靠匹配异常文字。
供应商请求标识可以进入受控证据，帮助定位上游问题。对客户端则返回最小必要信息，完整异常细节不能随意穿透服务边界。

原文依据：1.7 6.3 定义统一结果；1.7 6.5 错误也必须是协议；1.7 12.2 错误归一化

04:43  兼容入口仍须收紧范围
关键判断：只承诺可治理的字段，未知字段明确拒绝

兼容并不要求第一版复制全部字段。平台只支持自己明确治理的子集，未知字段应立即拒绝，静默忽略会让调用方误以为某项能力已经生效。
入口先验证调用凭据，获得可信租户身份，再做请求校验与基础限流。供应商密钥仍留在网关，客户端使用的是访问网关的凭据。
如果直接允许请求指定任意供应商地址，就能绕过路由和审计。如果接受某参数却在适配时丢掉，也会出现表面兼容但行为不一致。
验收要使用熟悉的兼容客户端调用服务，同时故意提交未知字段与未支持能力。正确结果是明确失败，而且供应商调用次数保持为零。

原文依据：1.7 7.1 为什么兼容接口仍需要收紧范围；1.7 7.2 API Schema；1.7 7.4 FastAPI 路由；1.7 15.9 扩展设计：验收标准

05:38  返回协议与扩展空间
关键判断：内部结果映射到外部形态，扩展信息独立命名

内部结果还要映射成外部兼容响应，比如选择列表、助手消息、结束原因和 Token 用量。这样内部领域模型不会被外部字段绑死。
路由入口根据是否流式选择普通返回或服务器发送事件。两种出口共享服务编排，不能为了不同协议各自复制一套调用治理。
网关附加的实际供应商、重试和切换信息，应放在独立命名空间，并明确哪些扩展仅内部调用者可见，避免与兼容字段混淆。
如果只把请求 JSON 原样转发，参数治理、能力检查、模板版本、解释路由和精确证据都可能消失。网关应执行契约，而不只是转发网址。

原文依据：1.7 7.4 FastAPI 路由；1.7 7.5 返回 OpenAI Compatible 响应；1.7 7.6 不要把 Gateway 做成透明代理

06:32  能力注册与协议适配
关键判断：能力决定候选资格，Adapter 不制定路由策略

能力注册表不能只是模型名字到客户端的字典。端点还要声明流式、JSON、结构约束、工具调用、视觉以及上下文和输出上限。
价格、优先级与启用状态也进入配置。它们不一定全部参与每次决策，但为预算判断、健康过滤和候选排序提供明确依据。
适配器只把内部请求翻译为供应商协议，再归一化结果。它不能自己选提示词、决定质量优先级或修改企业 Agent 的业务状态。
适配层仍关闭 SDK 隐藏重试，由网关统一记录真实尝试。接入另一个端点时，能力声明要验证实际行为，不能仅复制配置文件。

原文依据：1.7 8.1 Adapter 只适配协议，不制定业务策略；1.7 8.2 能力注册表；1.7 16.3 迁移验收：能不能接入另一个 Provider？

————————————————————————————————————————

07:25  路由先过滤再排序
关键判断：路由选择必须满足能力、策略、健康和预算

差旅助手需要结构化决策，候选端点有一个便宜快速模型和一个原生结构模型。第一步不是挑最强或最便宜，而是筛掉不满足能力的候选。
接着再检查租户预算、区域与数据策略、启用状态和健康情况。能力合格但处于熔断状态的端点，也不能继续作为本次首选。
合格候选才进入明确的优先级或评分规则。最后返回路由决定，包含选中端点、候选列表、拒绝原因和选择理由。
如果没有候选满足要求，就明确失败。这个顺序保证质量和协议约束不会被价格排序覆盖，也让事后能解释为什么调用了某个端点。

原文依据：1.7 8.3 路由不是“挑最强模型”

————————————————————————————————————————

08:18  新候选必须经过评测
关键判断：路由变更会改变 Agent 行为，需要固定样本证据

逻辑模型名没变，实际端点变化，Agent 的行为仍可能变化。因此路由调整不是纯运维配置，需要在固定评测集上验证新的候选。
差旅案例可同时比较任务成功率、结构合法率、工具选择、平均循环步骤、延迟和成本。一个更便宜的调用，可能因多轮返工反而增加任务总费用。
还要比较拒答与安全行为，不能因为一个端点更宽松就将其视为恢复通道。内容拒答之后换模型绕过，不属于正常故障切换。
路由测试也应断言为什么其他候选被拒绝。例如快速端点不支持结构约束，应记录明确原因，而不是只断言最后选择了另一个端点。

原文依据：1.7 8.5 路由与 Eval 的关系；1.7 8.4 Fallback 的边界；1.7 14.2 Router 测试

————————————————————————————————————————

09:14  三种输出共享执行主链
关键判断：普通、流式和结构化仅在结果消费阶段分化

普通输出、流式和结构化不应该成为三个独立系统。它们共享规范化、提示词解析、路由、超时、取消、错误映射和预算，只在结果消费阶段分化。
执行器先创建调用记录，记录路由决定，再执行有限恢复，校验结果，最后回写统一证据。失败也要留下完整调用记录。
但把观测写在最终收尾中，要防止写入失败覆盖原始异常。模型本来成功，数据库短暂不可用，不应该无条件把成功请求改成服务器错误。
观测故障需要独立告警与恢复策略。审查实现时同时看成功和失败路径，确认主链没有复制，记录错误也不会改变已经发生的调用事实。

原文依据：1.7 9.1 三种能力不是三个独立系统；1.7 9.2 普通调用执行器

————————————————————————————————————————

10:11  内部事件与唯一终态
关键判断：完成、失败、取消只能有一个成为终态

供应商分块先转成内部事件，再编码为外部 SSE。事件包含调用标识、事件标识和序列号，表达开始、文本、用量、完成、失败或取消。
唯一终态意味着一次调用只能在完成、失败和取消中选一个。不能先记完成，随后又因客户端断开记取消，否则前端和账本会互相矛盾。
模型完成、超时和客户端断开可能并发发生。扩展设计用原子比较并更新状态，让只有一个收尾动作获得终态写入权。
客户端连接结束只是现象，正常完成还需明确证据。用量回写也应跟随唯一收口，避免终态竞争导致同一次调用重复记账。

原文依据：1.7 9.3 Streaming 的内部事件；1.7 9.4 流式响应必须只有一个终态；1.7 14.4 Streaming 测试

————————————————————————————————————————

11:06  取消传播与背压
关键判断：下游离开或消费过慢时，上游资源也要收束

用户关闭差旅助手页面，不代表供应商模型自动停止。网关和运行框架要将取消信号传到后台任务、网络请求，以及相关可取消执行。
另一种问题是消费者太慢。模型产生事件快于客户端读取，若队列无限增长，长连接会逐渐吃满内存，这就是背压需要解决的资源问题。
事件队列应设置容量与写入等待边界。超过边界可以明确失败或取消，但不能随意丢弃终态、错误、用量或工具参数事件。
验收要模拟客户端断开和慢消费者，观察上游是否停止、队列是否有界，以及完成、失败、取消是否只出现一种，账本是否只落一次。

原文依据：1.7 9.4 流式响应必须只有一个终态；1.7 12.6 Backpressure；1.7 15.4 扩展设计：第三轮，Streaming 与取消

12:01  结构验证不能跳过
关键判断：半个 JSON 和合法结构都不能直接执行工具

结构化输出有两层保证：供应商生成约束，以及网关本地类型校验。即使端点声明支持结构约束，也不能省略本地验证。
差旅计划对象可能字段齐全，却要求操作其他员工订单。结构合法不能证明权限合法，业务规则与授权仍然必须在工具执行前检查。
流式 JSON 中途经常是不完整对象。看到动作名称或半个参数，就执行查询或修改，会把未经验证的候选内容变成真实副作用。
第一阶段可以流式显示状态，等完整对象结束后一次提交；或使用明确的类型化字段完成事件。两种方式都要经过完整校验和权限判断。

原文依据：1.7 9.5 Structured Output 的两层保证；1.7 9.6 Structured Streaming 的边界；1.7 15.5 扩展设计：第四轮，Structured Output

12:56  一次修复也要计入预算
关键判断：格式修复是有边界的新调用，不是无限重试

模型输出结构非法时，可以做一次专门修复。修复的目的明确，是修正结构错误，而不是拿同样请求无限重复生成。
扩展设计要求修复使用新的调用标识，并关联原调用，同属一个任务预算。修复消耗的 Token 和费用不能消失在成功响应后面。
只向修复模型提供必要的错误信息，避免把内部策略或敏感异常全塞进提示词。返回以后仍要再次验证结构和业务规则。
如果达到修复上限，就返回明确错误。不能改成未经校验的自然语言再交给 Agent，否则原本可靠的结构出口会在失败路径上被绕开。

原文依据：1.7 9.7 输出修复要有边界；1.7 十五、项目实战：Mini LLM Gateway；1.7 14.5 Structured Output 测试

13:48  Prompt Bundle 冻结行为
关键判断：可复现版本必须绑定提示词周边契约

提示词发布包，也就是 Prompt Bundle，不只是一份模板文件。模型行为还受示例、输入结构、输出结构、工具定义和默认参数影响。
差旅模板文字没变，但输出结构改了，或工具参数发生变化，旧调用就未必能复现。因此这些依赖也要绑定到可发布版本。
发布包还包含上下文预算和固定评测集。一个模板从课堂演示走向企业服务，需要明确资源范围，并用同样样本比较候选版本。
调用记录保存名称、版本和内容指纹。即使文件名没变，内容指纹也能暴露不可追踪修改，减少所谓同一版本实际内容不同的问题。

原文依据：1.7 十、第五阶段——Prompt 装配；1.7 10.1 Prompt Bundle 的组成；1.7 10.2 推荐目录结构；1.7 10.4 Prompt Registry

14:41  严格渲染与请求模式
关键判断：变量缺失应提前失败，两种系统提示来源不能冲突

模板装配先验证变量的输入结构，再执行严格渲染。缺失变量应该立即报错，不能静默变成空字符串，让模型在约束缺失的情况下生成。
项目笔记描述受限或沙箱渲染，这让模板执行范围受控；变量的业务含义、长度和必填规则仍然需要工程师决定。
网关可以提供直接消息模式，也可以提供模板与变量模式。两者的系统提示来源必须明确，不能同时传完整消息和模板变量造成冲突。
企业内部 Agent 更适合受控模板模式，因为版本、默认参数、结构和评测可以一起治理。调用前完成检查，也能避免无效请求浪费模型预算。

原文依据：1.7 10.3 使用严格模板渲染；1.7 10.4 Prompt Registry；1.7 10.5 Prompt API 与直接 Messages API

15:36  灰度必须在任务内稳定
关键判断：同一 Run 固定版本，行为变化才可归因

差旅助手一轮使用旧版模板，下一轮随机使用候选版，最后结果变好了还是变坏了，都很难归因。多轮任务内部应该保持版本稳定。
灰度分流使用租户、用户或任务标识等稳定键，通过固定规则选择版本。选定以后写入任务状态，不在每次模型调用时重新随机。
候选版本先在固定评测集比较，再小范围灰度。记录版本和内容指纹，才能把效果、延迟和成本变化关联到真实配置。
这也是冻结上下文的重要含义。冻结的不是用户所有输入永远不变，而是本次调用使用的模板、结构和策略证据在执行中保持明确。

原文依据：1.7 10.6 Prompt 灰度不是随机改模板；1.7 15.7 扩展设计：第六轮，Prompt Bundle

————————————————————————————————————————

16:29  追踪关联与延迟分解
关键判断：首个业务增量定义 TTFT，分段耗时解释瓶颈

一条完整因果链把任务追踪、运行、步骤和模型调用关联起来，工具调用则与模型调用并列。网关负责调用内部细节，框架负责完整任务关系。
追踪还要记录逻辑模型、实际端点、候选与拒绝原因、提示词指纹、结构版本、尝试次数和结果状态，才能回答为何选中这个服务。
首个文本时间，也就是 TTFT，应以第一个有业务意义的增量为准。连接建立或开始事件不能算首段内容，否则体验指标会过于乐观。
总耗时还应拆成排队、模板装配、路由、网络连接和生成。延迟上升时，分段数据才能判断应该优化并发、配置还是供应商响应。

17:25  账本价格与监控分工
关键判断：成本按当次价格版本估算，监控维度保持可控

费用账本使用版本化价格表，把未缓存输入、缓存输入和输出分别估算。不能用今天的单价回算很久以前的调用，否则历史费用会失真。
估算成本与供应商最终计费也要区分。账本保留真实用量与价格依据，之后才有条件分析差异，而不是只存一个没有来源的总数。
指标系统适合聚合错误率、限流比例和延迟分位数；追踪记录适合定位某次调用；日志保留受控排查细节，账本保留资源与费用证据。
用户标识、任务标识和完整提示词不适合作为监控标签，取值太多会导致基数膨胀。敏感正文默认也不进入普通日志，需要单独控制采样和权限。

18:21  按生命周期治理失败
关键判断：发生阶段决定恢复方式，retryable 不是自动许可

失败发生的位置决定恢复方式。认证和请求校验失败，应立即停止；模板缺变量，要修正请求；无兼容端点，需要配置或能力变化。
连接抖动、暂时过载和首块前限流，可以在预算内恢复。已经输出文本后断流，则不能从头生成拼接，输出结构错误应进入专门修复。
错误协议中的可重试标志只是一个条件，不是任何时候自动重试的许可。执行器还要检查剩余时间、费用和是否已经输出内容。
内容拒答也有不同语义，不能将其当成服务不可用，再切到更宽松模型绕过。稳定错误映射让上层按真实原因作判断，而不是盲目碰运气。

19:17  退避、截止时间与切换
关键判断：每次恢复同时受次数、时间和候选预算限制

只设置最大重试次数不够，三次长超时可能超过整个任务剩余时间。每次尝试都要按统一截止时间计算剩余额度，包括等待也必须受限。
指数退避让等待上限逐渐增长，随机抖动减少大量请求同步冲击供应商。若下一次等待已经越过截止时间，就不应睡完再继续调用。
同端点重试、切换候选和熔断是不同动作。前者恢复瞬时故障，切换尝试另一个合格端点，熔断则暂时过滤持续不健康端点。
所有尝试记录真实次数，并坚持首块文本边界。没有隐藏 SDK 循环，才可以对预算和证据负责；候选耗尽后也要明确收口。

20:12  只限制 QPS 仍会堆积
关键判断：长请求需要并发、队列和 Token 资源治理

假设每秒接入十个请求，每个生成持续三十秒，在没有其他限制时，在途请求可能积累到几百个。每秒速率合格，不代表资源安全。
因此除了 QPS，也要控制租户并发、供应商并发、全局并发和模型 Token 速率。令牌桶控制到达速度，信号量控制同时执行数量。
排队也会消耗用户等待与任务截止时间。剩余时间不足时，可以明确拒绝或选择其他合格资源池，而不是无限排队直到过期。
笔记项目的限流和熔断在进程内存中。多副本各算各的，会使总限制失真，生产演进需要共享状态，并通过指标验证限制真实生效。

21:07  幂等键不能保证不重复计费
关键判断：逻辑去重与供应商执行去重是两种保证

客户端超时后重新提交，可能让网关创建两个逻辑调用。幂等键可以关联重复提交，保存状态和已经存在的响应，减少平台侧重复执行。
但是同一个键必须对应同一请求指纹。如果用户换了任务内容仍复用旧键，就应拒绝，不能把旧结果当作新请求的答案。
还要保存上游请求标识，帮助判断调用是否已经送出。网关侧逻辑去重，并不自动代表供应商侧不会生成两次。
除非上游也提供相应保证，超时和重连仍可能重复计费。设计必须明确自己承诺到哪一层，不能把一个请求头解释成全链路只执行一次。

22:01  模型端口接回任务框架
关键判断：调用预算来自 Run，模型文本不能决定真实终态

企业 Agent 通过稳定模型端口请求动作，不导入供应商 SDK。网关客户端实现这个端口，内部处理服务请求与统一响应，循环只消费合法动作或稳定错误。
运行框架把剩余 Token、费用和截止时间传播到单次调用。重试、备用切换和结构修复都消耗同一任务预算，不能每次调用重新获得完整额度。
网关负责调用内部细节，任务框架关联运行、步骤、模型调用和工具调用。这样从最终答案可以追溯到检索、决策和执行证据。
差旅助手是否真正完成，要看业务条件与工具观察。模型输出结束文字只是候选陈述，网关不执行真实工具，也不扩大权限或伪造任务成功。

23:00  沿请求读项目模块
关键判断：模块拆分为独立演进与验证提供边界

读项目不要从文件名逐个背函数，应该沿一次差旅请求走。入口模块完成身份、限流和分流，编排模块装配提示词并执行候选恢复。
上游模块负责供应商网络通信，结构模块负责提取与校验，提示词模块负责版本渲染，用量模块负责持久化账本和流检查点。
配置来自 YAML 和环境变量，应用生命周期负责组装依赖。这样供应商、路由、提示词与 HTTP 入口可以分别调整，也可以单独测试。
容器和健康检查证明服务能交付，但仍不证明行为正确。部署验收要结合自动化测试与静态检查，并确认凭据配置和实际运行入口一致。

23:57  六类测试证明失败边界
关键判断：证明错误不穿透、次数真实、终态用量只落一次

第一组是适配器契约测试，验证文本、结束原因、用量、分块和错误映射；第二组是路由测试，不只证明选了谁，还证明为什么拒绝其他候选。
第三组验证重试次数、截止时间与候选上限，注入时钟、随机数和等待函数，不必让测试真的睡眠。第四组验证流顺序、取消、背压和唯一终态。
第五组准备合法对象、代码块包装、语法错误、类型错误、缺字段、额外字段、业务冲突和修复上限。错误对象不能进入 Agent 循环。
第六组检查成功、重试、切换和失败都有证据，实际次数一致，用量只记一次，日志没有密钥和未获允许的敏感正文。证据比接口成功更重要。

24:54  七轮实战与最终复习
关键判断：先定边界，再用 AI 补实现，用故障证明规格

实战按七轮推进：先用假的适配器跑内部契约，再接真实端点，加入流式与取消、结构校验、模型路由、提示词发布包，最后资源与观测治理。
先自己画对象边界，写出入口校验、规范化、冻结上下文、选候选、预算内执行、验证结果和只收口一次的伪代码，再让 AI 补样板。
最终口头验收要求两分钟讲清主链，代码验收要补骨架并抓住错误路径，迁移验收则重新判断新供应商的能力、事件、错误、价格与候选资格。
把未知字段、缺变量、认证失败、限流、超时、非法输出、首块后断流、取消和预算耗尽都变成可重复测试。你能解释并证明边界，才真正完成这一阶段。
