1.6 LLM Gateway
让企业 Agent 的每次模型调用都有统一边界、失败治理与真实证据

说明：根据第一章学习笔记整理，采用本地中文合成旁白。

00:00  企业 Agent 为何需要网关
关键判断：网关把模型调用收成可治理的平台能力

假设企业差旅助手要回答报销问题，客服助手要分析工单，评测脚本还要批量跑样本。三个系统都直接调用模型，密钥、超时、重试和结果校验就会出现三套实现。
统一模型网关，英文叫 LLM Gateway，解决的是调用治理。它把业务请求变成受控模型调用，再把供应商结果收成统一响应，使多个 Agent 可以共享可靠的执行入口。
本节的目标不是默写四百行代码。我们要能解释边界、补出主链、审查错误实现，再证明修复有效。AI 可以写样板，你需要决定哪些行为允许发生。
这节课沿一次企业 Agent 调用展开。先定义输入，再装配提示词，接着路由与适配，最后处理结构化输出、流式结果、重试和证据记录。

原文依据：1.6 一、为什么要学习 LLM Gateway？；1.6 1.2 本节怎样才算掌握？

01:04  四个角色各负其责
关键判断：任务决策与模型通信必须分开

运行框架，也就是 Harness，负责当前任务为什么要调用模型，结果怎样进入下一轮。网关负责这一次调用怎样合法发出、如何恢复故障以及返回什么证据。
供应商适配器，也就是 Provider，把平台请求翻译成某一类供应商协议，并归一化响应。模型则根据输入生成候选内容，它不会替平台承担权限或完成条件。
如果差旅业务规则写进网关，其他 Agent 的规则也会不断加进来，网关最终变成业务中心。如果供应商字段进入任务循环，换模型就必须修改任务逻辑。
判断归属可以问一句话：这是模型连接与调用恢复，还是任务状态与业务决策？超时属于前者，补上下文、换工具和重新规划属于后者。

原文依据：1.6 二、统一术语？；1.6 2.3 哪些内容属于 Gateway，哪些必须留在 Harness？

————————————————————————————————————————

02:06  四种标识不能混用
关键判断：按任务、调用、供应商和业务对象分别关联

差旅助手完成一次咨询，可能先检索制度，再分析例外，最后生成答案。这是一个任务运行，却会发出多次网关请求，所以任务标识和请求标识粒度不同。
供应商返回的响应标识适合向上游排查，业务系统的差旅单号适合查询领域对象。二者都不能代替平台请求标识，否则日志关联会失去稳定性。
本节原型先实现请求标识，是明确的阶段范围。以后接入完整运行框架，再由上层注入可信的任务标识，把多轮调用关联起来。
这里尤其不能让模型自己生成追踪标识。标识承担证据关联职责，应由系统创建或验证；模型输出只是候选内容，不是可信的执行记录。

原文依据：1.6 2.2 请求 ID、Trace ID 和业务 ID 为什么不能混用？

03:05  统一契约不是请求透传
关键判断：网关必须拥有自己的输入与输出协议

统一契约，英文叫 Canonical Contract，是网关自己承诺的请求、响应和错误协议。它决定上层可以使用哪些能力，而不是任意供应商参数都能透传。
看示例里的额外字段禁止规则。如果调用方偷偷加入某家供应商的私有参数，入口立即拒绝。这样平台协议不会被不同 Agent 各自依赖的字段撕开。
消息角色、内容长度、消息数量和超时范围都有工程目的。它们限制资源消耗，缩小错误空间，并让请求在到达模型以前就能完成确定性检查。
审查时如果看到请求直接接收任意字典，或者路由直接返回供应商 SDK 对象，就要追问契约是否存在。统一了网址，仍然可能没有统一行为。

04:05  能力组合在入口就检查
关键判断：未支持的组合必须在产生输出前拒绝

统一请求包含逻辑模型名、消息、是否流式、输出结构、超时和提示词选择。每个字段都回答一个具体问题，字段越多，平台需要承担的组合复杂度也越高。
原型明确拒绝流式输出与响应结构同时使用，因为它没有增量 JSON 解析能力。这是能力边界，而不是模型会不会生成 JSON 的简单问题。
设想已经发出半段结构化文本，最后才发现不合法。客户端看到的内容无法撤回，普通 HTTP 错误也已经来不及返回，错误处理会变得复杂。
因此第一版要先决定支持哪些组合，入口就拒绝未实现组合。验收不仅看错误状态码，还要断言供应商调用次数为零，证明错误没有越过边界。

05:06  提示词按名称版本装配
关键判断：模板资产受控，变量仍要按输入边界处理

企业差旅助手提交的不是一整段系统提示词，而是知识决策模板的名称、版本和变量。网关从受控模板库读取正文，再把产品名称等变量装配进去。
这个做法让一次调用能够回答用了哪个提示词版本。模板升级不必修改每个 Agent，效果回退时也可以区分模型变化和提示词变化。
模板不存在或者变量缺失，应当在模型调用前停止。带着残缺提示词继续调用会增加成本，还可能生成看似合理但缺少约束的错误结果。
受控模板并不自动消除提示词注入。变量如果来自用户或外部资料，仍是不可信输入；能否进入系统消息、长度怎样限制，需要你明确设计。

原文依据：1.6 3.2 为什么 Prompt 选择要成为请求的一部分？；1.6 3.4 Prompt 模板怎样装配进消息？；1.6 7.3 检查点二：Prompt 是否可复现？

06:04  先阻止无效请求出门
关键判断：确定性错误应消耗零次模型调用

把企业差旅助手的产品名称变量删掉，模型会不会被调用？这是第一阶段最有价值的故障注入。返回四百错误还不够，必须证明上游调用次数为零。
再加入一个未声明字段，或指定不存在的模板版本。三类错误的共同点是同样输入不会自行变好，因此不应该进入网络重试或备用模型切换。
测试可以用假的供应商实现，记录每次收到的请求。它固定输出，不需要真实网络，能直接证明装配顺序和错误边界，而不是碰运气看线上返回。
第一阶段验收通过，意味着我们拿到合法且已装配的统一请求。接下来才有资格把逻辑模型名解析为地址、密钥和能力配置。

原文依据：1.6 3.4 Prompt 模板怎样装配进消息？；1.6 3.5 第一阶段怎样验收？；1.6 7.6 检查点五：测试能否证明失败边界？

07:01  逻辑模型名隔离部署变化
关键判断：上层请求服务类别，网关解析真实端点

差旅助手只请求平台的主逻辑模型，不需要知道真实供应商型号。网关通过模型配置把这个名字解析成具体模型、地址、密钥来源和能力。
这样部署切换通常不会进入任务循环。但逻辑名字稳定，不意味着行为完全相同，团队仍需要验证新的真实模型是否满足任务要求。
配置里最关键的不是地址，而是能力声明。备用模型必须支持本次请求所需的结构化能力，否则主模型超时后切换会变成新的协议错误。
模型是否在允许列表中，也应该在供应商调用前检查。开放任意模型名或任意地址会使治理失效，平台无法再解释调用去了哪里。

原文依据：1.6 4.1 为什么平台模型名不能直接等于供应商模型名？；1.6 6.3 fallback 为什么必须先做能力检查？

07:56  适配器只暴露稳定能力
关键判断：普通与流式接口截断供应商对象

Provider 协议只暴露两种稳定能力：普通调用返回完整文本与用量，流式调用产出文本增量。供应商响应里的具体对象和字段被截断在适配层。
如果路由、重试和任务循环都读取某家 SDK 的选择列表，接入另一种协议时就要到处修改。适配器隔离变化，让多数执行逻辑可以保留。
第一版只有一个兼容协议适配器，也不必提前写五个空实现。但接口边界应该先存在，否则后续测试很容易依赖供应商 SDK 类型。
我们可以用假的 Provider 验证主链，再用契约测试验证真实适配器。前者证明平台策略，后者证明协议翻译，两种证据各有用途。

原文依据：1.6 4.2 Provider Protocol 为什么比直接调用 SDK 多一层？；1.6 5.1 普通模型调用怎样隔离供应商响应？

————————————————————————————————————————

08:52  密钥与重试必须收口
关键判断：隐藏的 SDK 重试会让次数和预算失真

企业 Agent 只访问内部网关，供应商密钥由网关环境读取。密钥轮换、供应商变更和访问审计集中在这一处，避免凭据扩散到多个业务项目。
缺少密钥是配置错误，不是网络瞬时故障。继续用相同配置重试没有恢复意义，应该返回稳定错误，并在受控环境修复配置。
这里有个容易被 AI 忽略的参数：关闭 SDK 内置重试。因为外层网关已经有重试预算，再留一层隐藏循环，真实调用数就可能相乘。
例如 SDK 一次外部调用内部发三次，网关再试两次，日志可能只写两次，实际已经六次。次数不真实，成本、延迟与故障判断都会失真。

原文依据：1.6 4.3 为什么 API Key 只能留在 Gateway？；1.6 6.2 为什么要关闭 SDK 重试，再由 Gateway 统一执行？

————————————————————————————————————————

09:48  兼容接口仍有能力差异
关键判断：接受相同字段不代表提供相同保证

兼容接口降低了通信适配成本，却没有消除工程责任。不同服务可能在结构化模式、用量字段、流式块和异常类型上存在差异。
原生 JSON Schema 模式把结构作为接口约束。JSON Object 模式主要要求返回 JSON，具体结构通过提示词描述，两者提供的保证不能混为一谈。
差旅助手需要带动作和答案的决策对象，只得到合法 JSON 仍可能漏字段或类型错误。接口接受响应格式参数，不等于它真的支持严格结构约束。
因此适配器负责模式转换，模型配置负责声明真实能力，网关负责共同校验出口。三层各自承担职责，不能只靠一个兼容标签作判断。

原文依据：1.6 4.4 OpenAI Compatible 为什么仍然需要适配？；1.6 5.2 Structured Output 为什么有两种发送方式？

————————————————————————————————————————

10:47  合法 JSON 仍要复验
关键判断：只有解析与结构校验都通过才产生 parsed

模型正常返回文本，只说明生成完成。网关先做 JSON 语法解析，再做结构约束校验，只有两层都通过，解析对象才能进入统一响应。
比如差旅决策缺少必填动作字段，文本仍可能是合法 JSON。语法解析不会发现这个问题，结构校验才会阻止它进入下游执行链。
当前原型只发现错误并返回稳定错误码，没有自动纠错循环。把结构错误当成网络重试，会混淆模型服务故障与结果格式问题。
以后加入格式修复，也要单独限制修复次数并记录额外用量。网关验证通用结构，结束动作必须带答案等业务组合仍由差旅 Agent 自己验证。

原文依据：1.6 5.3 模型已经返回 JSON，为什么还要在 Gateway 校验？；1.6 7.7 接入 Agent Loop 时，哪一段需要替换？

11:43  真正流式从增量开始
关键判断：每个上游增量到达后应立即向下转发

真正的流式处理，是供应商一产生增量，适配器就提取文字，网关随后编码成服务器发送事件，也就是 SSE，立即交给客户端。
如果先等模型生成完，把完整答案存起来，再分几段发送，视觉上虽然像逐段显示，却没有缩短用户等待首段内容的时间。
供应商原始分块不能穿过适配器边界。网关只需要知道新增文本，今后换另一家服务，客户端事件协议仍然可以保持稳定。
第一版内部事件包括文本增量、正常完成和流内失败。它已经能建立闭环，但只产出文字的 Provider 还不足以承载最终用量和所有完成状态。

原文依据：1.6 5.4 Streaming 为什么不能先收完整答案再转发？；1.6 5.5 为什么流式成功不能只看“连接关闭了”？

————————————————————————————————————————

12:36  断开连接不等于成功
关键判断：客户端只能凭明确完成事件确认流成功

差旅助手已经显示了两段政策解释，连接突然关闭。用户看见内容不代表答案完整，系统更不能因为读循环结束就自动标记成功。
客户端必须收到明确的完成事件，才把本次流标成成功。如果遇到错误，应收到明确失败事件，这样部分内容和最终状态可以分开处理。
流开始之后，HTTP 状态码通常已经发出，无法再改成服务器错误。失败必须成为流协议的一部分，不能只在后台记一句异常然后断开。
原型的供应商层仅返回文本，没有携带上游完成事件和用量。讲解时要承认这个边界，后续升级成类型化事件，才能把完成证据和计费收得更严。

原文依据：1.6 5.5 为什么流式成功不能只看“连接关闭了”？；1.6 8.2 Streaming Token Usage 应该从哪里取得？

13:33  先分类错误再决定恢复
关键判断：重试只处理可能自行恢复的瞬时故障

不能把所有异常都变成重试。连接抖动、超时和限流可能短暂恢复，认证失败、未知模型或缺模板变量，则不会因为重复提交而变好。
结构校验失败又是另一类。供应商已经成功生成内容，问题发生在结果出口，应该进入格式修复或明确失败，而不是伪装成模型不可用。
当前笔记代码列出了可重试异常，没有宣称覆盖所有服务端错误。如果要增加服务过载分类，必须同时补映射和测试，避免讲义与代码不一致。
错误分类的意义是使恢复策略有因果依据。审查 AI 代码时，看到宽泛捕获后直接重试，就应要求说明每类错误为什么值得再试。

原文依据：1.6 6.1 为什么不能写成 except Exception: retry？

14:29  重试次数必须是真实调用
关键判断：attempts 记录所有候选上的实际尝试总数

沿笔记的原型推演一次故障：主模型第一次连接失败，等待后第二次仍失败，随后备用模型成功。最终尝试次数应当是三，实际模型是备用模型。
这个数必须对应真实上游请求，而不是只记录循环外层次数。关闭 SDK 内部重试，就是为了让网关能够完整掌握实际尝试证据。
固定短等待适合学习原型，生产演进可以引入指数退避与随机抖动。但等待时间增长并不自动安全，还需要总时间和费用预算约束。
验收用 Provider Stub 依次制造失败、失败、成功，然后同时断言调用顺序、总次数和实际模型。只看到最后成功，会漏掉预算失控。

原文依据：1.6 6.2 为什么要关闭 SDK 重试，再由 Gateway 统一执行？；1.6 8.4 Provider 级指数退避应该加在哪里？

————————————————————————————————————————

15:26  备用模型须满足同一能力
关键判断：恢复调用不能偷偷降低协议要求

备用切换，英文叫 Fallback，目标是恢复同一次请求。输入、提示词和结果协议仍然相同，因此备用模型必须满足这次请求的全部能力要求。
差旅助手要求决策对象，主模型超时后如果切到只会普通文本的模型，基础设施故障就变成了协议故障。返回一句自然语言不能算等价恢复。
原型当前主要检查结构化输出能力，这是第一版范围。以后支持工具调用、视觉或长上下文，也应把这些条件纳入候选资格。
能力检查属于模型配置和路由，不应该把每家供应商差异硬塞进重试函数。候选没有合格端点，就明确返回错误，而不是换模型碰运气。

原文依据：1.6 6.3 fallback 为什么必须先做能力检查？；1.6 4.1 为什么平台模型名不能直接等于供应商模型名？

————————————————————————————————————————

16:22  首块文本是切换边界
关键判断：已经输出文本后不能透明切模型续写

流式调用要以是否已经向用户输出文字为边界。首块以前，客户端还没有看到模型内容，暂时失败可以按预算重试或切换备用。
首块以后从头生成，会把两段不同答案拼在一起。可能出现重复开头、断句、风格变化，甚至前面说允许报销，后面却生成相反条件。
因此原型用已经输出的状态标记决定停止恢复，并发送流失败事件。客户端可以保留部分内容，但不能将这段中断内容当成完整成功。
有些系统能在保存状态与专门协议支持下重连，这不能被复制为无条件自动重试。恢复动作和它依赖的状态必须一起设计。

原文依据：1.6 6.4 流式 fallback 为什么以“是否已经输出”为边界？；1.6 7.5 检查点四：执行主链是否只有一个入口？

————————————————————————————————————————

17:17  网关重试与任务重试不同
关键判断：上层必须把调用尝试纳入任务总预算

网关重试保持输入、模板、结构和目标不变，只恢复模型服务的瞬时故障。任务循环重试可能补充上下文或换工具，任务状态已经变化。
差旅助手找不到制度，决定再检索一次，是业务决策，不是网关网络恢复。把两类重试混在一起，会让失败原因和预算归属难以理解。
如果一次网关调用最多尝试四次，任务循环又重新执行三轮，一个步骤就可能发出十二次模型调用。各层局部限制都成立，总消耗仍可能失控。
运行框架应读取尝试次数、成本和错误码，将每次模型调用计入任务预算。网关提供调用证据，任务层决定还值得继续多少轮。

18:13  统一响应与可信 Trace
关键判断：响应告诉上层结果，Trace 解释调用事实

统一响应保留原始文本，通过校验后才包含解析对象，还要返回实际模型、用量、耗时和尝试次数。上层因此无需读取供应商 SDK 对象。
实际模型尤其重要。请求的是主逻辑模型，最后可能由备用模型生成；如果日志只写请求模型，质量变化、费用和故障定位都会被误导。
结构化调用证据，也就是 Trace，记录请求标识、提示词版本、模型、用量、成本、延迟、状态与稳定错误码，才能按维度聚合和复盘。
Trace 不等于默认保存全部提示词和回答。正文可能含业务数据和个人信息，保存范围、期限和访问权限应单独决定，不能因调试方便全量扩散。

19:12  用五个检查点审查代码
关键判断：沿边界读实现，比逐行背代码更有价值

阅读完整网关时，抓五个检查点：统一契约、可复现提示词、供应商隔离、唯一受控执行路径，以及证明失败边界的测试。这样不需要逐行背诵实现。
如果命令行、测试脚本和线上路由各自直接调用 Provider，就会长出多套能力校验与重试策略。调用应走受控入口，差异才能集中治理。
测试除了成功，还要验证未知模型和缺变量时零调用，连接失败后次数准确，非法 JSON 不产生解析对象，首块后断流不访问备用模型。
最后检查证据本身。失败也必须记录 Trace，日志不应含密钥、普通响应不应暴露内部堆栈。能返回成功，远不足以证明系统可靠。

20:09  把结果接回企业 Agent
关键判断：网关负责通用校验，Agent 继续验证业务规则

差旅助手构造网关请求，声明主逻辑模型、用户任务、知识决策模板和决策对象的结构。网络返回后，先把响应解析成统一响应类型。
如果没有通过校验的解析对象，就不能继续当作决策使用。接着 Agent 再验证业务规则，例如结束动作必须有答案，检索动作必须有查询内容。
这一步仍然必要，因为通用结构规则不能覆盖所有业务组合，更不能证明制度事实真实。结构合法是进入业务判断的条件，不是业务正确的结论。
任务循环根据验证后的决策选择检索、继续回答或结束。网关不执行这些业务工具，也不因为模型说完成了，就替任务框架修改真实终态。

21:06  扩展能力放在正确位置
关键判断：先保持主链，再替换适配与存储设施

后续流式用量要在 Provider 取得，再映射为内部完成或用量事件。路由和 Agent 不应直接理解某家供应商的流式参数与响应字段。
接入新的响应协议，应新增相应 Provider，把文本增量、完成、失败和未完成状态映射为内部事件。执行主链仍消费统一协议。
指数退避的配置可以独立管理，但执行仍由网关循环控制。不要把完整重试重新藏进适配器，否则普通与流式可能形成两套恢复策略。
Trace 持久化则替换记录接口，使用仓储负责写库和查询。先让契约、恢复和证据真实可靠，再扩展复杂路由、跨区容灾等设施。
