# 第二章笔记的练习题和答案 

### 一、复习题与参考答案

1. **Function Calling 为什么不等于函数已经执行？**
Function Calling 只让模型生成工具名称、候选参数和调用 ID，表达“想执行什么”。真正执行必须由应用程序接收 Tool Call，经过 Runtime 的参数校验、权限检查、审批和业务预检查后，再调用 handler。因此，模型提出动作不等于系统已经执行动作。

2. **Tool Schema、ToolDefinition 和 handler 分别面向谁？**
Tool Schema 面向模型，说明工具名称、用途和可提交的参数；ToolDefinition 面向 Registry、Snapshot 和 Runtime，保存完整契约、治理规则及实现引用；handler 面向数据库、API 等业务系统，执行确定的业务动作。模型不应看到密钥、数据库连接和内部权限配置。

3. **为什么模型不能填写用户、租户、角色和审批？**
模型输出是不可信输入，可能生成错误信息，也可能受提示注入影响。如果允许它填写身份和授权字段，就相当于允许调用者自行声明权限。这些事实必须来自登录态、服务端身份、权限系统和审批记录；模型只能提供订单号、金额、原因等候选业务参数。

4. **`tool_call_id`****、****`trace_id`**** 和业务 ID 有什么区别？**
`tool_call_id` 标识一次具体工具调用，用于关联调用、执行事件和结果；`trace_id` 关联整条请求或任务调用链；业务 ID 标识真实业务对象，例如 `order_id`。一次任务可以包含多个工具调用，多个调用也可以操作同一业务对象。`tool_call_id` 不能直接替代跨调用的业务幂等键。

5. **Registry、工具发现和模型选工具为什么是三件事？**
Registry 管理系统有哪些工具和版本；工具发现根据 Agent 职责、用户权限、运行模式、启停和依赖状态筛选本轮候选集合；模型从这个集合中选择要申请的动作。注册不代表开放，开放不代表选用，选用也不代表获得执行授权。

6. **为什么版本路由必须发生在 Snapshot 之前？**
Snapshot 要冻结已经选定的工具版本，让模型看到的 Schema 与 Runtime 执行的 handler 保持一致。如果创建快照后再切换版本，就可能出现“模型按 v1 参数申请，系统用 v2 实现执行”的版本漂移。因此应先完成版本路由和灰度选择，再创建快照。

7. **为什么启停和依赖需要发现时与执行前两次检查？**
发现时检查，避免模型围绕不可用工具制定计划；执行前复查，防止模型思考期间工具被紧急停用、权限收回或依赖失效。Snapshot 固定版本，但不能让旧快照绕过最新的紧急停用与安全限制。

8. **`prepare → execute → finalize`**** 的顺序写错会产生什么后果？**
`prepare` 应先完成校验、可信上下文注入和授权；`execute` 才能调用 handler；`finalize` 负责输出校验、脱敏、审计和结果包装。权限检查晚于执行，会导致先产生副作用再拒绝；脱敏晚于消息回写，会导致敏感数据已经泄漏；执行时重新查全局 Registry，会破坏快照一致性。

9. **Function Calling、MCP、Runtime 和 Agent Loop 怎样分工？**
Function Calling 让模型表达结构化调用意图；MCP 标准化外部能力的发布、发现和调用；Runtime 对每次调用实施确定性的校验、授权和受控执行；Agent Loop 接收结果，决定继续调用、修改计划、等待审批、询问用户或结束。它们分别解决“提出动作、接入能力、执行治理、持续决策”。

10. **Tool、Resource 和 Prompt 应该怎样选择？**
需要参数并执行查询或副作用动作时使用 Tool，例如查询订单、创建工单；有稳定 URI、可重复读取的只读上下文使用 Resource，例如订单状态说明；由用户显式选择的参数化任务模板使用 Prompt。Prompt 可以引导行为，但不能替代业务授权。

11. **为什么 MCP Tool 必须先适配成内部 ToolDefinition？**
这样本地与远端工具才能共享注册、快照、校验、权限、审批、超时、结果治理和审计机制。Adapter 负责限定名、协议转换、错误映射及结果归一化，MCP 协议对象留在适配层内部。Agent Loop 不应为不同 Server 编写绕过 Runtime 的特殊执行分支。

12. **白名单、RBAC、资源授权和人工审批分别回答什么问题？**
白名单回答“当前 Agent 和任务能否使用这个工具”；RBAC 回答“当前主体是否具备这类业务权限”；资源授权回答“能否操作这个具体订单、文件或租户资源”；人工审批回答“具备资格的主体是否确认了这次具体高风险动作”。审批不能替代权限，业务权限也不能替代资源归属检查。

13. **为什么审批必须绑定规范化参数摘要，并且只能使用一次？**
审批确认的是具体动作，不是工具的永久执行权。审批应绑定用户、租户、工具、规范化参数摘要、有效期和使用状态。批准退款 100 元后改成 399 元，旧审批必须失效；使用后不能再次授权新的执行。并发场景下，一次性状态还需要原子校验与消费，防止重复执行。

14. **Tool Runtime 重试与 Agent Loop 重新决策有什么区别？**
Runtime 重试用于恢复明确的瞬时故障，保持工具、参数和业务意图不变；Loop 重新决策根据失败结果修改参数、切换工具、调整计划或询问用户。参数错误、权限拒绝和审批缺失不能靠原样重试解决。各层应明确重试责任，避免重试次数相乘，并共同消费 Run 的次数、时间和成本预算。

15. **为什么写操作超时不能直接判断失败并重试？**
超时只证明调用方没有及时收到结果，不证明下游没有执行。退款可能已经成功，只是响应丢失，直接重试会重复退款。非幂等写操作应返回 `TIMEOUT_UNKNOWN`，先查询业务状态、对账或转人工；只有具备可靠幂等键、去重表或唯一约束时，才适合受控重试。

16. **Sandbox 与权限治理分别解决什么问题？**
Sandbox 限制代码或进程能访问哪些文件、网络、系统资源及执行能力；权限治理判断当前主体能否执行某项业务动作。前者约束执行环境，后者约束业务资格。一个进程即使在 Sandbox 内，也可能通过获准访问的 API 发起越权业务请求，因此两者需要配合。

17. **为什么 Tool Result 进入模型前还要限长、脱敏和归一化？**
原始结果可能过长、包含凭证和个人信息、暴露内部异常，或带有提示注入文本。限长控制上下文体积；脱敏减少泄漏；归一化提供稳定的成功与错误协议。同时应保留来源和 `tool_call_id`，把外部文本当作数据，不赋予其指令权限。

18. **Audit 与 Trace 为什么不能互相替代？**
Trace 主要解释调用链如何流动、哪里耗时或失败；Audit 主要证明谁以什么身份、依据什么规则触发了什么业务动作。它们应通过任务和调用 ID 关联，但记录目的与内容不同。“策略放行”和“业务执行成功”也应分开记录，审计故障不能把已成功的业务动作改写为失败并诱发重试。

19. **为什么安全测试必须断言 handler 调用次数和真实副作用？**
返回拒绝错误，不代表动作没有执行：错误实现可能先退款再返回 `PERMISSION_DENIED`。测试必须同时检查返回协议、handler 调用次数和数据库记录或外部请求等副作用证据。被拒绝的调用应做到 handler 零调用、真实副作用为零，并保留原始调用 ID。

20. **阶段二项目怎样证明本地、Python 和 MCP 工具共用同一治理入口？**
将不同来源的能力统一适配为 ToolDefinition，注册并进入 Snapshot，所有调用都经过 `ToolRuntime.invoke()`。用相同契约测试验证各来源：非法参数、越权、缺审批和工具停用都在副作用前被拒绝；成功与失败都保留调用 ID，并产生可关联的审计与 Trace。不能只靠代码结构判断，还要用调用探针证明不存在绕行路径。

**审查题：AI 生成的代码有哪些典型错误需要识别？**
应能发现六类问题：

1. 权限检查位于副作用之后；

2. SDK、Runtime 和 Loop 重复承担重试；

3. 把写操作超时当作确定失败；

4. 原始异常、Token 或客户数据进入模型和日志；

5. 测试只检查错误文本、不检查副作用；

6. Tool Result 丢失原始调用 ID。
